对返回结果再做一次业务侧精确校验：

```go
actualModel := twin.Metadata.Model

if matchedConfig != nil &&

   requiredMappingsComplete(matchedConfig) {
```

### 6. 根据 manifest 读取累计量

核算任务根据 manifest 中冻结的 `cumulative_telemetry_ref`，从 `metrics.samples` 查询两个窗口。

核算 `10:00–10:30`，首版 `W=10m`：

```text
上一尾值：查询 09:50–10:00，取事件时间最晚值
当前尾值：查询 10:20–10:30，取事件时间最晚值
```

假设：

```text
previous_tail = 12500 Wh
current_tail  = 12750 Wh
scale         = 0.001
```

标准化并计算：

```text
previous = 12500 × 0.001 = 12.5 kWh
current  = 12750 × 0.001 = 12.75 kWh
usage    = 12.75 - 12.5 = 0.25 kWh
```

然后写入自动用量事实和 `usage_points.samples` 当前投影。

**FactKey 是什么**

用户真正想得到的是：

> 表具 A 在 10:00 到 10:30 这半小时用了多少电？

这个问题对应一条“半小时用量事实”，它的唯一身份就是 `FactKey`：

```text
FactKey = (
  meter_id,
  energy_type_id,
  slot_start_utc,
  slot_width
)
```

例如：

```text
meter_id        = xtwin://twins/twin-101
energy_type_id  = electricity-uuid
slot_start_utc  = 2026-08-29T02:00:00Z  // 上海时间 10:00
slot_width      = 30m
```

它唯一表示：

```text
表具 twin-101
+ 电
+ 上海时间 10:00～10:30
这一格用量
```

定义见[设计文档](D:/xbrother/R5/xtwin-insight/doc/能效2.5/2026-08-27-meter-energy-accounting-billing-design.md:364)。

`FactKey` 不是任务 ID，也不是测点 ID。它是最终业务结果的主键。

同一个 `FactKey` 可以产生多个版本：

```text
第一次定时核算：0.25 kWh
晚到数据修复：  0.27 kWh
人工修正：      0.30 kWh
撤销人工修正：  回到 0.27 kWh
```

这些版本都在回答同一个问题，所以 `FactKey` 不变。

```text
FactKey
  ├─ AutoRevision 1 = 0.25
  ├─ AutoRevision 2 = 0.27
  ├─ Manual SET     = 0.30
  └─ 当前有效值      = 0.30
```

**四个核心概念**

```text
WorkflowOperation：为什么要做这一批工作
TaskSnapshot：     用什么固定输入做
TaskShard：        哪一小批由 worker 执行
FactKey：          最终要产生哪一格业务结果
```

以两块表为例：

```text
一个 Operation
  └─ 一个 Snapshot
       └─ 一个 Shard
            ├─ FactKey(A, 电, 10:00)
            └─ FactKey(B, 电, 10:00)
```

### WorkflowOperation

它代表一次完整业务操作，是进度和结果的观察单位。

示例：

```text
operation_id = op-1030
```

表示“本次 10:00～10:30 定时核算”。

| 示意字段 | 含义 |
|---|---|
| `operation_id` | 这次操作的唯一编号，用于查询进度和追踪日志 |
| `type` | 操作来源，例如正常定时、自动修复、页面范围重算 |
| `priority` | worker 调度等级，例如 `SCHEDULED`、`REPAIR`、`BULK` |
| `status` | 整体状态，例如等待、执行中、成功、失败 |

需要注意：文档定义了优先级种类，但没有正式确定 `type/status` 枚举和完整字段。

一个 operation 可以包含很多 shard。只有所有必要阶段完成，operation 才算成功。

### TaskSnapshot

Snapshot 是这次计算使用的不可变输入。

```text
snapshot_id       = snap-1030
config_generation = 12
manifest_id       = manifest-1030
slot              = [10:00, 10:30)
business_timezone = Asia/Shanghai
W                 = 10m
```

各字段含义：

| 字段 | 含义 |
|---|---|
| `snapshot_id` | 这份快照的唯一编号 |
| `config_generation` | 使用第几版能源配置，例如累计量映射、单位换算和增量上限 |
| `manifest_id` | 使用哪一份有效表具清单，包括表具及其实际测点映射 |
| `slot` | 本次核算哪个半小时范围 |
| `business_timezone` | 日期、半小时边界和价格时段按哪个业务时区解释 |
| `W` | 从槽尾向前多长时间寻找尾样本，首版为 10 分钟 |
| 尾样本规则 | 在窗口中按事件时间选择最后一条样本 |

其中 `config_generation` 和 `manifest_id` 不是一回事：

```text
config_generation = 计算规则
manifest_id       = 按规则解析出的表具名单
```

即使配置一直是 generation 12，每个半小时的 manifest 也可能不同：

```text
10:00 manifest：A、B
10:30 manifest：A、B、C  // 新增了一块表
11:00 manifest：A、C     // B 被删除
```

Snapshot 的核心价值是：worker 重试时仍使用同一份配置、表具名单和测点映射，不能重新读取最新配置。

### TaskShard

Shard 是 worker 真正领取并执行的最小任务。

例如：

```text
operation_id  = op-1030
shard_id      = shard-0
snapshot_id   = snap-1030
fact_keys     = [FactKey-A, FactKey-B]
ready_at      = 10:40
attempt_count = 0
lease_owner   = null
```

| 字段 | 含义 |
|---|---|
| `operation_id` | 归属哪次完整操作 |
| `shard_id` | 当前分片编号 |
| `snapshot_id` | 执行时必须读取哪份快照 |
| `fact_keys` | 当前分片负责计算哪些业务结果 |
| `ready_at` | 最早允许执行的时间 |
| `attempt_count` | 已尝试多少次 |
| `lease_owner` | 当前由哪个 worker 占有 |
| `lease_deadline` | worker 最晚持有到什么时候 |
| `next_attempt_at` |失败后何时允许重试 |
| 检查点 | 分片已经执行到哪个阶段 |

`ready_at=10:40` 是因为：

```text
槽结束时间 = 10:30
W          = 10m
ready_at   = 10:30 + 10m
```

必须等到当前尾值窗口的数据基本到达后再计算。

### intent_revision

`intent_revision` 解决“同一 FactKey 被多个任务同时计算，谁最终生效”。

例如：

```text
定时任务：
FactKey-A -> intent_revision 105

稍后提交的范围重算：
FactKey-A -> intent_revision 106
```

即使定时任务最后才执行完：

```text
105 后完成
106 先完成
```

当前投影仍然只能采用 106。因为业务优先级按提交顺序判断，不按完成时间判断。

**把整个任务创建过程串起来**

```text
1. 确定目标槽 [10:00, 10:30)

2. 从 manifest 找到表具 A、B

3. 为每块表构造 FactKey
   A + 电 + 10:00 + 30m
   B + 电 + 10:00 + 30m

4. 创建 WorkflowOperation
   表示“做这一批半小时核算”

5. 创建 TaskSnapshot
   冻结配置、manifest、测点、时区和 W

6. 为每个 FactKey 预留 intent_revision

7. 把 FactKey 分批放入 TaskShard

8. 设置 ready_at = 10:40

9. worker 到时间后领取 shard
```

现在最需要记住的是：

```text
Operation 管整体
Snapshot 管固定输入
Shard 管执行批次
FactKey 管一条最终业务结果
```

下一步可以在这个模型上继续看：worker 领取一个 `TaskShard` 后，怎样根据其中的 `FactKey` 和 `TaskSnapshot` 拼出 `metrics.samples` 查询，并提交一个用量版本。

继续从这个分片开始：

```text
TaskShard shard-0
  snapshot_id = snap-1030
  fact_keys:
    - FactKey-A：表具 A + 电 + 10:00～10:30
    - FactKey-B：表具 B + 电 + 10:00～10:30
```

worker 的目标是为这两个 `FactKey` 各产生一条半小时用量事实。

**第一步：FactKey 找到实际测点**

`FactKey` 只说明“算哪块表、哪种能源、哪个时间槽”，不包含测点名称。

必须结合 Snapshot 中冻结的 manifest：

```text
FactKey.meter_id
  -> snapshot.manifest_id
  -> EffectiveMeterMember
  -> 唯一累计量映射
  -> TelemetryRef
  -> metrics.samples 中的实际序列
```

例如 manifest 内容：

```text
表具 A
  meter_id          = xtwin://twins/twin-101
  cumulative_point  = total_energy
  source_series     = series-A
  raw_unit          = Wh
  standard_unit     = kWh
  scale             = 0.001
  offset            = 0

表具 B
  meter_id          = xtwin://twins/twin-200/components/branch-1
  cumulative_point  = total_energy
  source_series     = series-B
  raw_unit          = kWh
  standard_unit     = kWh
  scale             = 1
  offset            = 0
```

所以：

```text
FactKey-A -> series-A
FactKey-B -> series-B
```

这里再次暴露了设计文档的一个缺口：`source_series` 如何由设备/组件遥测点转换成 `metrics.samples.__name__`，尚未正式定义。但执行任务必须在 manifest 中冻结这个结果，不能让 worker 临时推导。

**第二步：计算查询窗口**

目标槽为：

```text
S = [10:00, 10:30)
W = 10m
```

需要两个尾值窗口：

```text
上一槽尾值窗口：[09:50, 10:00)
当前槽尾值窗口：[10:20, 10:30)
```

中间的 `10:00～10:20` 不参与尾值选择。

逻辑查询类似：

```sql
SELECT series_id, event_time, value
FROM metrics.samples
WHERE series_id IN ('series-A', 'series-B')
  AND (
       event_time >= '09:50' AND event_time < '10:00'
    OR event_time >= '10:20' AND event_time < '10:30'
  )
ORDER BY series_id, event_time
```

这里只是逻辑 SQL。实际字段仍要根据 `metrics.samples` 的物理结构确定。

**第三步：按序列选择尾值**

假设查到：

```text
series-A：
  09:55  12480 Wh
  09:59  12500 Wh   <- previous_tail
  10:21  12600 Wh
  10:29  12750 Wh   <- current_tail

series-B：
  09:58  50.0 kWh   <- previous_tail
  当前窗口无数据
```

每个窗口只取事件时间最晚的一条。

所以：

```text
A.previous_tail = 12500 Wh @ 09:59
A.current_tail  = 12750 Wh @ 10:29

B.previous_tail = 50.0 kWh @ 09:58
B.current_tail  = 不存在
```

同一事件时间有两条不同值时，文档明确不定义决胜规则。因此上游存在冲突重复时，重算结果可能不稳定。

**第四步：标准化并计算**

表具 A：

```text
previous = 12500 × 0.001 = 12.50 kWh
current  = 12750 × 0.001 = 12.75 kWh
usage    = 12.75 - 12.50 = 0.25 kWh
```

结果：

```text
status      = NORMAL
reason_code = 空
usage       = 0.25
```

表具 B 缺少当前尾值：

```text
status      = MISSING
reason_code = MISSING_CURRENT_TAIL
usage       = null
```

这里要区分两种失败：

```text
没有尾样本
-> 成功生成一条 MISSING 业务事实

ClickHouse 查询失败、单位配置损坏
-> TaskShard 技术失败，不生成伪造的 MISSING
```

`MISSING` 是合法业务结果，不代表任务执行失败。

状态规则见[设计文档](D:/xbrother/R5/xtwin-insight/doc/能效2.5/2026-08-27-meter-energy-accounting-billing-design.md:400)。

**第五步：构造 AutoUsageRevision**

表具 A 生成：

```text
AutoUsageRevision
  FactKey
    meter_id       = xtwin://twins/twin-101
    energy_type_id = electricity-uuid
    slot_start_utc = 02:00Z
    slot_width     = 30m

  auto_revision       = 7
  intent_revision     = 105
  snapshot_id         = snap-1030
  config_generation   = 12
  manifest_id         = manifest-1030

  previous_tail_time  = 09:59
  previous_raw_value  = 12500
  previous_std_value  = 12.50

  current_tail_time   = 10:29
  current_raw_value   = 12750
  current_std_value   = 12.75

  usage               = 0.25
  status              = NORMAL
  reason_code         = null
  input_fingerprint   = hash(...)
  calculation_hash    = hash(...)
  write_id            = usage-op1030-A
```

表具 B 同样生成一条修订，只是：

```text
current_tail = null
usage        = null
status       = MISSING
reason_code  = MISSING_CURRENT_TAIL
```

`AutoUsageRevision` 是追加历史，不会修改旧版本。字段要求见[设计文档](D:/xbrother/R5/xtwin-insight/doc/能效2.5/2026-08-27-meter-energy-accounting-billing-design.md:433)。

**第六步：写入自动修订**

worker 使用预留的稳定 `write_id` 写入：

```text
usage_points.auto_revisions
```

例如：

```text
usage-op1030-A -> A 的 auto revision 7
usage-op1030-B -> B 的 auto revision 4
```

worker 重试时仍使用相同 `write_id`：

```text
第一次写成功，但响应丢失
-> 第二次使用相同 write_id 重试
-> 不产生语义重复版本
```

**第七步：更新当前有效投影**

自动修订写入后，还不能直接成为页面当前值。必须经过 `EffectiveFactProjector`。

对表具 A，先检查有没有人工锁。

没有人工修正：

```text
当前最高 intent_revision = 105
本次 intent_revision     = 105
-> A 当前值更新为 0.25 NORMAL
```

如果之前人工 `SET 0.30`：

```text
最新人工动作 = SET
-> 当前值继续保持 0.30 MANUAL_CORRECTED
-> 自动 0.25 只保存为候选
-> manual_conflict = true
```

如果后来执行人工 `CLEAR`：

```text
最新人工动作 = CLEAR
-> 回到最高有效自动版本
-> 当前值变成 0.25 NORMAL
```

最终当前结果写入：

```text
usage_points.samples
```

它才是页面和下游唯一允许读取的用量入口。

**第八步：确认输出并产生事件**

ClickHouse 写入和当前投影成功后，关系库记录：

```text
FactKey-A + intent 105 + write_id -> WRITTEN
FactKey-B + intent 88  + write_id -> WRITTEN
```

然后写入 outbox：

```text
AutoUsageRevisionReady
UsageEffectiveChanged
```

大致语义：

```text
AutoUsageRevisionReady
-> 自动历史版本已经存在

UsageEffectiveChanged
-> 当前有效值发生变化
-> 唤醒汇总和成本计算
```

如果人工锁导致当前有效用量没有变化，是否仍发布 `UsageEffectiveChanged`，文档没有明确说明。合理语义应当是：只有有效投影或其有效版本真正变化时才发布。

**第九步：完成 Shard**

A 和 B 都产生了合法业务结果：

```text
A = NORMAL  0.25
B = MISSING null
```

因此：

```text
shard-0.status = SUCCEEDED
success_count  = 2
normal_count   = 1
missing_count  = 1
```

B 的 `MISSING` 不会导致 shard 失败。

只有类似这些情况才让 shard 进入重试：

```text
metrics.samples 查询失败
ClickHouse 写入失败
快照内容损坏
单位转换契约损坏
租约丢失
```

到这里，完整链路是：

```text
TaskShard
-> FactKey
-> Manifest 中的累计量 TelemetryRef
-> metrics.samples 两个尾值窗口
-> 标准化和质量判定
-> AutoUsageRevision
-> EffectiveFactProjector
-> usage_points.samples
-> outbox
```

下一步就是沿 `UsageEffectiveChanged` 看它如何同时触发用量汇总和成本任务。

先给结论：

- 租约用于保证同一时刻只有一个 worker 负责某个 `TaskShard`。
- 租约不能单独保证业务正确，还要配合 `write_id`、`intent_revision` 和幂等写入。
- 新设计文档记录了 `attempt_count`、`next_attempt_at` 等字段，但**没有规定最大重试次数**。当前文档语义下存在无限重试风险，需要补充。

**1. 任务状态流转**

建议明确为：

```text
PENDING
   |
   | worker 领取并取得租约
   v
RUNNING -----------------------> SUCCEEDED
   |
   | 可重试错误
   v
RETRY_WAIT
   |
   | 到达 next_attempt_at
   v
PENDING

RUNNING
   |
   | 不可重试错误 / 超过最大次数
   v
FAILED

PENDING / RETRY_WAIT
   |
   | 用户取消
   v
CANCELLED
```

已经进入 `RUNNING` 的任务不因取消而回滚；设计文档明确“取消只阻止尚未开始的分片”。

**2. worker 怎样取得租约**

假设分片：

```text
operation_id  = op-1030
shard_id      = shard-0
status        = PENDING
ready_at      = 10:40
lease_owner   = null
lease_deadline = null
attempt_count = 0
```

`10:40` 后，`worker-01` 尝试领取：

```text
status         = RUNNING
lease_owner    = worker-01
lease_deadline = 10:45
attempt_count  = 1
```

领取必须是数据库原子操作，条件至少包括：

```text
status 是 PENDING/RETRY_WAIT
ready_at <= 数据库当前时间
next_attempt_at <= 数据库当前时间
租约不存在或已经过期
```

可以使用 `SELECT ... FOR UPDATE SKIP LOCKED`，也可以使用带条件的 `UPDATE ... RETURNING`。

必须使用数据库时间，不能依赖不同 worker 的本地时钟。

**3. 为什么还需要 lease_epoch**

只有 `lease_owner` 不够。建议增加：

```text
lease_epoch
heartbeat_at
```

示例：

```text
10:40 worker-01 领取
      lease_epoch = 7
      deadline = 10:45

10:43 worker-01 崩溃

10:45 租约过期

10:46 worker-02 重新领取
      lease_epoch = 8
      deadline = 10:51
```

如果 `worker-01` 在 `10:47` 恢复，它已经是过期 worker。更新 shard 状态时必须携带：

```text
lease_owner = worker-01
lease_epoch = 7
```

数据库发现当前 epoch 已经是 8，拒绝它更新状态。这叫 fencing，防止旧 worker 把新 worker 的结果覆盖掉。

文档目前没有定义 `lease_epoch`，这是租约协议中的缺口。

**4. worker 怎样续租**

任务执行时间可能超过 5 分钟，因此 worker 需要心跳：

```text
每隔 lease_duration / 3 续租一次
```

例如租约 5 分钟，则约每 1 分钟续租：

```text
UPDATE workflow_shard
SET lease_deadline = database_now + 5m,
    heartbeat_at = database_now
WHERE operation_id = ?
  AND shard_id = ?
  AND lease_owner = ?
  AND lease_epoch = ?
  AND status = RUNNING
```

续租失败时，worker 应停止继续处理新的输出，因为它可能已经失去任务所有权。

已经提交的输出不回滚，通过 `write_id` 幂等处理。

**5. 什么叫任务执行成功**

假设 shard 包含两个 `FactKey`：

```text
FactKey-A -> NORMAL 0.25
FactKey-B -> MISSING null
```

虽然 B 是 `MISSING`，但它仍是合法业务事实，因此两个输出都成功。

一个 shard 只有完成以下动作才可以标记成功：

```text
1. 所有 FactKey 都生成了业务事实
2. auto_revisions 已按 write_id 幂等写入
3. usage_points.samples 当前投影已处理
4. 关系库已确认输出写入状态
5. outbox_event 已持久化
6. 所有输出均有明确结果或检查点
```

然后在关系库事务中：

```text
workflow_shard.status = SUCCEEDED
lease_owner           = null
lease_deadline        = null
finished_at           = database_now
```

只要求 outbox 已经持久化，不要求消息已经发送成功。Outbox publisher 可以之后继续重试发送。

**6. shard 成功后 Operation 怎么处理**

每个 shard 结束后，汇总所属 operation：

```text
总 shard 数      = 10
成功 shard 数    = 8
运行中 shard 数  = 1
等待 shard 数    = 1
```

只有所有必要 shard 成功，当前阶段才成功。

普通半小时核算可以是：

```text
用量 shard 全成功
-> 用量阶段成功
-> UsageEffectiveChanged 唤醒汇总和成本
```

页面范围重算要求更严格：

```text
用量事实
-> 用量汇总
-> 成本事实
-> 成本汇总
-> WorkflowOperation 才 SUCCEEDED
```

文档对范围重算已经明确这一点，但普通定时 operation 是否包含成本阶段还没有完全定义。

**7. 任务失败后怎么处理**

首先区分三类结果。

业务异常，不重试：

```text
缺少尾值            -> MISSING，任务成功
累计量回退          -> BAD，任务成功
增量超过上限        -> BAD，任务成功
```

临时技术错误，可以重试：

```text
ClickHouse 超时
XTwin/单位服务暂时不可用
数据库连接失败
租约意外丢失
Outbox/投影暂时写入失败
```

永久技术错误，不应反复重试：

```text
TaskSnapshot 内容损坏
冻结的测点引用无法解析
单位换算契约非法
程序不支持 payload_version
```

可重试错误进入：

```text
status          = RETRY_WAIT
last_error_code = CLICKHOUSE_UNAVAILABLE
next_attempt_at = database_now + backoff
lease_owner     = null
lease_deadline  = null
```

重试必须继续使用原来的：

```text
snapshot_id
intent_revision
auto_revision
write_id
```

不能重新生成一套版本。

**8. 最大重试次数**

**文档事实**：目前只写了“尝试次数、下一次执行时间、按策略重试”，没有定义：

```text
max_attempts
退避算法
永久失败状态
死信处理
人工重试入口
```

因此当前设计确实不完整。

建议增加：

```text
max_attempts = 8                 // 默认，可按任务类型覆盖
backoff      = 指数退避 + jitter
max_backoff  = 30m
```

示意：

```text
第 1 次失败：10 秒后
第 2 次失败：30 秒后
第 3 次失败：1 分钟后
第 4 次失败：2 分钟后
第 5 次失败：5 分钟后
后续逐步增加，最高不超过 30 分钟
```

达到最大次数后：

```text
workflow_shard.status = FAILED
failure_class         = RETRY_EXHAUSTED
workflow_operation    = FAILED
```

同时：

```text
产生告警
进入 reconciliation 待处理清单
保留 snapshot、检查点和最后错误
不向 usage_points.samples 写入 FAILED
```

后续可以由人工重试或 reconciliation 创建新的 `REPAIR` operation。旧 shard 保持终态，不建议把它无限复活。

**9. 一个重要的崩溃场景**

如果 ClickHouse 已写入，但 worker 在关系库确认前崩溃：

```text
ClickHouse：已有 write_id = usage-op1030-A
关系库：仍显示未确认
shard：租约最终过期
```

新 worker 重试时先按 `write_id` 检查：

```text
已经写入
-> 不重复产生版本
-> 补关系库确认
-> 补 outbox
-> 完成 shard
```

所以租约负责“谁执行”，`write_id` 负责“重复执行也只有一个结果”，`intent_revision` 负责“并发任务谁最终生效”。三者职责不同。

当前设计最需要补充的就是：`lease_epoch`、最大重试次数、错误分类、退避算法和 `FAILED` 后的重新驱动方式。
我已确认最新文档：租约、最大重试次数、redrive 和物理序列解析都已经补上。现在继续看用量任务成功之后发生什么。

先沿用表具 A：

```text
FactKey-A
  表具：twin-101
  能源：电
  时段：10:00～10:30

有效用量：
  effective_usage_revision = U7
  usage                     = 0.25 kWh
  status                    = NORMAL
```

`U7` 表示这个 `FactKey` 当前生效的是第 7 个用量版本。

**1. 产生 UsageEffectiveChanged**

当 `usage_points.samples` 从旧有效版本变成 `U7` 后，关系库 outbox 写入：

```text
event_type               = UsageEffectiveChanged
aggregate_key            = FactKey-A
aggregate_revision       = U7
correlation_id            = op-1030
causation_id              = 自动用量修订事件 ID
```

事件 payload 至少需要让消费者知道：

```text
FactKey
effective_usage_revision = U7
usage_status              = NORMAL
usage                     = 0.25
business_timezone         = Asia/Shanghai
```

文档定义了统一事件 envelope，但各事件的 payload 还没有逐字段定义。这是后续需要补的协议。

事件会被至少投递一次，因此：

```text
UsageRollupConsumer 可能收到两次
CostingWorkflow     也可能收到两次
```

两个消费者都必须幂等。

**2. 第一条分支：重建用量汇总**

事件进入 `UsageRollupConsumer`：

```text
UsageEffectiveChanged
        |
        v
确定受影响周期
        |
        +-> HOUR：10:00～11:00
        +-> DAY：当天 00:00～次日 00:00
        +-> MONTH：当月
```

假设 10:00～11:00 有两条半小时事实：

```text
10:00～10:30  0.25 kWh  NORMAL
10:30～11:00  0.30 kWh  MANUAL_CORRECTED
```

汇总器不做：

```text
旧小时合计 + 0.25
```

而是重新查询这个小时内全部当前事实：

```sql
SELECT *
FROM usage_points.samples
WHERE meter_id = 'xtwin://twins/twin-101'
  AND energy_type_id = 'electricity-uuid'
  AND slot_start_utc >= hour_start
  AND slot_start_utc < hour_end
```

然后重新计算：

```text
expected_count = 2
normal_count   = 1
manual_count   = 1
missing_count  = 0
bad_count      = 0
valid_count    = 2
usage_total    = 0.25 + 0.30 = 0.55
rollup_status  = COMPLETE
```

写入 `usage_points.rollups`：

```text
RollupKey = (
  meter_id,
  energy_type_id,
  grain = HOUR,
  period_start_utc
)
```

为什么必须完整重扫：

```text
同一个事件重复到达
事实版本乱序到达
人工 SET/CLEAR
晚到数据重算
```

完整重扫都能得到相同当前结果，增量加减容易重复累计。规则见[设计文档](D:/xbrother/R5/xtwin-insight/doc/能效2.5/2026-08-27-meter-energy-accounting-billing-design.md:542)。

如果两条事实是：

```text
10:00～10:30  MISSING
10:30～11:00  0.30 NORMAL
```

则：

```text
valid_count    = 1
missing_count  = 1
usage_total    = 0.30
rollup_status  = ABNORMAL
```

`MISSING` 不当作零参与合计。

**3. 第二条分支：创建成本任务**

`CostingWorkflow` 收到同一个事件后，先确认：

```text
FactKey-A 当前有效用量仍然是 U7
```

如果当前已经变成 `U8`，这个旧事件不应继续为 `U7` 创建当前成本。

确认后冻结成本快照：

```text
CostTaskSnapshot
  FactKey                  = FactKey-A
  effective_usage_revision = U7
  effective_usage          = 0.25
  usage_status             = NORMAL

  binding_revision         = B3
  price_plan_id            = plan-electricity
  price_plan_revision_id   = P9
  business_timezone        = Asia/Shanghai
  price_calendar           = 48 槽编译日历
```

其中：

```text
B3 = 任务创建时表具当前绑定的第 3 版
P9 = 根据业务日期选中的价格版本
```

随后为该 `FactKey` 预留：

```text
cost_intent_revision = 21
cost_revision        = 11
write_id             = cost-U7-B3-P9
```

成本任务同样进入 `WorkflowOperation -> TaskSnapshot -> TaskShard`，使用刚补充的租约和重试协议。

**4. 成本任务怎样选择状态**

worker 领取成本 shard 后，严格按这个顺序判断：

```text
NO_USAGE
-> NO_PRICE_PLAN
-> NO_PRICE_VERSION
-> COMPUTED
```

表具 A 的有效用量是：

```text
U7 = 0.25 kWh NORMAL
```

因此通过第一关。

快照里存在绑定 `B3`，通过第二关。

把 `slot_start_utc` 转成上海时间：

```text
2026-08-29 10:00
```

选择：

```text
effective_date <= 2026-08-29
```

的最新价格版本 `P9`。

计算半小时价格槽：

```text
slot_index = (10 × 60 + 0) / 30 = 20
```

假设第 20 槽为峰价：

```text
pricing_category = PEAK
unit_price       = 0.80 CNY/kWh
```

成本：

```text
cost_amount_raw = 0.25 × 0.80
                = 0.200 CNY
```

得到：

```text
cost_status = COMPUTED
```

半小时事实保存高精度 `0.200`，此时不做人民币两位小数舍入。

**5. 其他三种成本结果**

如果用量是 `MISSING/BAD`：

```text
cost_status = NO_USAGE
cost        = null
```

即使同时没有价格方案，也固定返回 `NO_USAGE`，因为它优先判定。

如果用量正常但没有绑定：

```text
cost_status = NO_PRICE_PLAN
cost        = null
```

如果存在绑定，但当天没有适用价格版本：

```text
cost_status = NO_PRICE_VERSION
cost        = null
```

如果单价为零：

```text
cost_status = COMPUTED
cost        = 0
```

零价格与缺少价格不能混淆。

**6. 写入成本事实和当前投影**

生成：

```text
CostFactRevision
  FactKey                  = FactKey-A
  cost_revision            = 11
  cost_intent_revision     = 21
  effective_usage_revision = U7
  binding_revision         = B3
  price_plan_revision_id   = P9
  pricing_category         = PEAK
  unit_price               = 0.80
  cost_amount_raw          = 0.200
  cost_status              = COMPUTED
  write_id                 = cost-U7-B3-P9
```

追加写入：

```text
usage_points.cost_revisions
```

然后尝试更新：

```text
usage_points.cost_samples
```

当前投影必须同时满足两个条件：

```text
cost_intent_revision 足够新
AND
effective_usage_revision 仍是当前有效用量版本
```

例如：

```text
成本任务 C21 正在计算 U7
此时人工修正产生 U8
U8 又创建成本任务 C22
```

即使 C21 最后才完成：

```text
C21 引用 U7，不能覆盖当前成本
C22 引用 U8，才是当前有效成本
```

这条约束见[设计文档](D:/xbrother/R5/xtwin-insight/doc/能效2.5/2026-08-27-meter-energy-accounting-billing-design.md:708)。

**7. 成本变化后重建成本汇总**

成本当前投影变化后产生：

```text
CostEffectiveChanged
```

成本汇总器重新扫描 `usage_points.cost_samples`，构造时、日、月成本汇总。

假设一小时两个槽：

```text
10:00  COMPUTED 0.20
10:30  NO_PRICE_PLAN null
```

则：

```text
expected_count       = 2
computed_count       = 1
no_price_plan_count  = 1
cost_amount_raw_total = 0.20
cost_completeness    = PARTIAL
```

如果全部是 `COMPUTED`：

```text
cost_completeness = COMPLETE
```

如果一个 `COMPUTED` 都没有：

```text
cost_completeness = MISSING
cost_total        = null
```

成本完整性与用量汇总状态是两套独立概念，见[设计文档](D:/xbrother/R5/xtwin-insight/doc/能效2.5/2026-08-27-meter-energy-accounting-billing-design.md:729)。

现在整条后半链路是：

```text
UsageEffectiveChanged
   |
   +-> UsageRollupConsumer
   |      -> usage_points.rollups
   |
   +-> CostingWorkflow
          -> CostTaskSnapshot
          -> CostTaskShard
          -> CostFactRevision
          -> usage_points.cost_samples
          -> CostEffectiveChanged
          -> usage_points.cost_rollups
```

下一步应该看页面查询：半小时、时、日、月分别读取哪张表，`COMPLETE/ABNORMAL/PARTIAL/MISSING` 最终怎样返回给前端。

你没搞懂是正常的，因为这张图省略了一个关键概念：**阶段屏障（stage barrier）**。

不是“所有半小时任务没结束，就开始计算最终日/月汇总”，而是：

- 单个半小时事实完成后，可以提前标记受影响汇总为待重建。
- 多槽范围重算必须等用量阶段完成，才发布最终汇总。
- 整个 operation 还要等成本阶段和成本汇总完成才能成功。

**先看正常半小时核算**

假设现在核算表具 A 的：

```text
10:00～10:30 用量
```

当这个 `FactKey` 已经成功写入：

```text
usage_points.samples
```

就可以重新计算表具 A 的：

```text
10:00～11:00 小时汇总
当天日汇总
当月月汇总
```

它不需要等待表具 B、C、D 全部完成，因为汇总键包含：

```text
meter_id + energy_type_id
```

表具 A 的汇总只依赖表具 A 自己的半小时事实。

此时当天还没有结束，未来槽不属于预期槽。例如当前到 `10:30`，日汇总只统计当天已经封口的半小时槽；之后每完成一个新槽，再覆盖重建一次日/月汇总。

**再看范围重算**

假设重算表具 A 的 `8 月 1 日`，当天有 48 个半小时 FactKey：

```text
00:00、00:30、01:00……23:30
```

如果第 1 个 FactKey 完成就立即重建日汇总，会出现：

```text
第 1 个完成  -> 重建一次
第 2 个完成  -> 再重建一次
...
第 48 个完成 -> 第 48 次重建
```

而且中间可能混合旧值和新值。因此范围重算不应让每条事件都立即发布最终汇总。

推荐流程是：

```text
UsageEffectiveChanged
  -> 只登记 DirtyRollupKey
  -> 不立即认定汇总阶段完成

当天全部 Usage FactKey 完成
  -> UsageShardCompleted
  -> 对 DirtyRollupKey 完整重建一次
  -> UsageRollupStageCompleted
```

这里的 `DirtyRollupKey` 类似：

```text
表具 A + 电 + HOUR + 10:00
表具 A + 电 + DAY + 08-01
表具 A + 电 + MONTH + 08-01
```

**完整阶段关系**

推荐把原图补成：

```text
UsageFactShard[]
       |
       | 所有目标 FactKey 已确认
       v
USAGE_FACTS_COMPLETED
       |
       +-------------------------+
       |                         |
       v                         v
UsageRollupShard           CostFactShard[]
       |                         |
       v                         | 所有成本事实完成
USAGE_ROLLUPS_COMPLETED           v
                          CostRollupShard
                                 |
                                 v
                          COST_ROLLUPS_COMPLETED
       |                         |
       +------------+------------+
                    |
                    v
          WorkflowOperation SUCCEEDED
```

用量汇总和成本事实可以并行，因为成本只依赖有效用量事实，不依赖用量汇总。

成本汇总必须等对应成本事实全部完成。

**事件在这里承担什么职责**

`UsageEffectiveChanged` 表示：

> 某个半小时有效用量发生了变化，相关汇总和成本已经失效。

它不是说：

> 整次范围重算已经完成，可以发布最终日/月结果。

因此消费者收到它后有两种处理方式：

| 场景 | 处理方式 |
|---|---|
| 正常单槽核算 | 可以立即合并并重建受影响汇总 |
| 范围重算、批量修复 | 先登记 dirty key，等日 shard 完成后批量重建 |
| 人工修正单个槽 | 立即重建对应时、日、月汇总 |
| 多个事件短时间集中到达 | 按 RollupKey 合并去重后重建 |

**范围重算失败时怎么办**

假设：

```text
8 月 1 日 usage shard 成功
8 月 2 日 usage shard 失败
8 月 3 日 usage shard 成功
```

那么：

```text
8 月 1 日可以完成最终汇总
8 月 3 日可以完成最终汇总
8 月 2 日保持原汇总或标记待重建
整个 WorkflowOperation 仍然是 FAILED/运行未完成
```

不能因为 8 月 2 日失败而回滚 8 月 1 日、3 日已经确认的事实。

**需要区分两类“汇总结果”**

1. 在线滚动汇总：

```text
当前已经封口的半小时槽汇总
随每个新槽不断覆盖更新
```

2. operation 最终汇总：

```text
本次范围重算的目标 FactKey 全部处理完成后
基于新事实统一重建并确认
```

范围重算期间，推荐继续对外返回上一版已确认汇总，等 `UsageRollupStageCompleted` 后再切换新的 `write_seq`，避免页面看到新旧事实混合的中间状态。

所以最准确的结论是：

> 单个半小时事实完成后可以提前触发“失效通知”，但多槽任务必须经过 `USAGE_FACTS_COMPLETED` 阶段屏障，才能确认新的日/月汇总。原图缺少这个屏障，容易误解成边算半小时边发布最终日/月结果。
现在看页面查询。核心原则先记住：

```text
页面永远不查原始 metrics.samples
页面也不直接查 auto_revisions/cost_revisions 历史表
页面只查当前投影和汇总投影
```

对应关系：

| 查询粒度 | 用量表 | 成本表 |
|---|---|---|
| 半小时 | `usage_points.samples` | `usage_points.cost_samples` |
| 时/日/月 | `usage_points.rollups` | `usage_points.cost_rollups` |

**7. 下钻逻辑**

用户从月下钻到日：



```text
MONTH -> DAY -> HOUR -> HALF_HOUR
```

**8. 分页与范围汇总是两件事**

假设查询一个月半小时数据，共 1488 行：

```text
page_size = 20
```

第一页只返回 20 条明细，但顶部范围汇总必须基于完整 1488 条：

```text
range_usage_total
range_cost_total
range_rollup_status
range_cost_completeness
各类异常数量
```

不能只汇总当前页。该约束见[设计文档](D:/xbrother/R5/xtwin-insight/doc/能效2.5/2026/08/27-meter-energy-accounting-billing-design.md:1004)。

明细使用基于周期起点的 keyset token，例如逻辑上包含：

```text
last_period_start_utc
grain
meter_id
energy_type_id
query_range_fingerprint
```

不能使用 `OFFSET 20`，因为事实更新后偏移分页容易重复或漏行。

文档只要求稳定 `page_token`，尚未定义 token 的编码、签名和过期策略。

**9. “暂无数据”和 MISSING 不一样**

查询范围内没有任何预期槽：

```text
表具当时尚未启用
或者已经停用
或者该范围没有有效 manifest
```

返回：

```text
rows = []
```

前端展示“暂无数据”。

如果该范围存在预期槽，但没有采集尾值：

```text
rows = [
  {
    usage_status: MISSING,
    usage: null
  }
]
```

这时不能展示“暂无数据”，因为系统知道本来应该有一条数据，只是它缺失了。

**10. 页面查询不暴露任务技术状态**

这些状态不进入用量事实：

```text
PENDING
RUNNING
RETRY_WAIT
FAILED
```

页面请求期间的“加载中”只是前端网络状态。

范围重算运行中，页面可以轮询：

```text
GetRangeRecomputeOperation
```

但不能把明细行状态改成“重算中”。旧事实继续可读，重算成功后由新有效版本替换。

页面读取链路最终可以概括为：

```text
ListEnergyMeters
  -> 选择表具

QueryMeterEnergyDetails
  |
  +-> HALF_HOUR
  |     -> samples + cost_samples
  |
  +-> HOUR/DAY/MONTH
        -> rollups + cost_rollups

Reader
  -> 完整范围汇总
  -> 稳定分页
  -> 状态与 null 原样返回
```

下一步可以继续看人工修正：用户在半小时行点编辑后，`base_effective_revision` 如何防止覆盖别人刚完成的修正，以及 `SET/CLEAR` 如何重新触发汇总和成本。
